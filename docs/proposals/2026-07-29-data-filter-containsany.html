#267 · array 成員運算子 containsany 去留

2026-07-29 · 比較 containsany 與既有 terms/contains/containsall,決定要不要在已發布的 @rfjs/data-filter 上留這個新運算子。

現況containsany L4 已加,只在 data-filter
既有可用eq / terms / containsall / contains
疑慮≈ terms 且跨引擎靜默降級

① 語意重疊:同一筆資料,四個運算子分別 match 什麼

範例陣列欄位 roles = ['manager', 'staff'],查詢值 ['manager', 'vip']。

運算子語意對 ['manager','staff'] 查 ['manager','vip']相等方式跨引擎可用
contains ∃ element 含 substring(逐元素子字串) 視子字串而定(例 'man' → match);刻意的 substring 語意 子字串 是
terms ∃ element 等於 ∃ 查詢值 'manager' 命中 → true loose == 是(可攜)
containsany 新 ∃ element 等於 ∃ 查詢值 'manager' 命中 → true transform-aware === 否 · 只有 data-filter
containsall ∀ 查詢值 ∈ elements 'vip' 不在 → false transform-aware === 否 · 只有 data-filter
eq ∃ element = 單一值(成員 of one) 查 'manager' → true transform-aware === 是
金底兩列 = 結果完全相同。containsany 與既有 terms 對同一輸入給同一答案,唯一差別是 terms 用 loose ==、containsany 用 transform-aware ===——不是新能力,是同一件事的第二個名字。

② 更關鍵:containsany 只在 data-filter → 製造新的跨引擎分岔

同一棵 filter tree 編到不同執行目標。用 containsany 的葉子:

葉子: roles containsany ['manager'] → data-filter ✅ 正確 match
同一葉子→ sql-filter ⚠ 不認得· pg-filter ⚠· jsonb ⚠· mongo / es ⚠
在 SQL/jsonb 端會 靜默降級 · match 不到(uncoverable / 無輸出),使用者不會看到錯誤。這正是 #279 在修的那類「跨引擎契約不一致 → 靜默失敗」的 bug——等於一邊統一 arity,一邊又新增一個 data-filter-only 詞彙把洞挖回來。用 terms 就沒這問題(它每個引擎都有)。

③ 三個選項

A. 移除 · 改用文件解 S(推薦) 拿掉 containsany;文件講清楚:terms=任一成員(可跨引擎)、containsall=全部、contains=刻意 substring。
零新詞彙 · 不製造分岔 · 正面回應 issue「精確成員其實已存在,只是不好發現」。
B. 保留 · 加文件標註 S 留著 containsany,README/matrix 註明它 ≈ terms 且 data-filter-only。
接受輕微重疊 + 跨引擎分岔;換得 containsany/containsall 命名對稱與更嚴格相等。
C. 所有引擎都加 L 把 containsany(+ containsall)實作進 sql/pg/jsonb(可能還有 mongo/es)、補 arity、更新 matrix。
真正跨引擎可用;但範圍大很多,是獨立一輪 spec,非本次 cluster。
建議 A:issue #267 真正要的是「array 精確成員」——那個能力 eq/terms/containsall 早就給了,缺的是可發現性與文件,不是再多一個運算子。真的想要 containsany/containsall 的對稱命名,就走 C 全引擎一起加。

待決:#267 選 A / B / C。 · 已定案:#268 補齊全 i-family(istartswith/iendswith/ieq/ineq);#266 三態、#278 validator、#279 arity→one 維持不動。
